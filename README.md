# FORMA — каталог людей на DummyJSON

Новый этап: `users.html`. В списке — горизонтальные карточки с аватаром, именем, ником и ID пользователя.
Нажатие открывает большое модальное окно из двух половин:
слева аватар, имя и описание человека; справа сверху повторяется та же карточка,
ниже находятся ID, имя, ник, роль, почта и телефон. Карточка примерно 380 × 132 CSS px
(ориентир 10 × 3,5 см, фактический размер на экране зависит от масштаба и устройства).
На телефоне половины идут друг под другом, карточка сужается по ширине экрана.
Это карточка самого пользователя, не публикация; отдельного автора или ID публикации нет.
`userCard(user)` в `users/details.js` рисует одинаковую карточку в списке и в окне.
Поиск по имени/нику, сортировка по имени в обе стороны, фильтр статуса.
**Статус — это роль: пользователь (`user`), модератор (`moderator`), админ (`admin`), не онлайн-статус.**

Простой HTML + CSS + JavaScript, без сборщика и библиотек.
Существующий товарный CRUD сохранён в `crud.html` и `crud/`; [его документация](docs/products.md).
Старые задания и профили команды находятся в `index.html`.

## Запуск

```bash
python3 -m http.server 8000
```

Открыть http://localhost:8000/users.html или запустить VS Code Live Server.
Нужен интернет. Не открывать через `file://`: используются JS-модули.

## Данные и API — общий договор для всех агентов

[Документация DummyJSON Users](https://dummyjson.com/docs/users), [репозиторий сервиса](https://github.com/Ovi/DummyJSON).

| Операция | Запрос |
| --- | --- |
| Прочитать людей | `GET /users?limit=0&select=firstName,lastName,username,image,email,phone,company,role` |
| Добавить | `POST /users/add` |
| Изменить | `PUT /users/{id}` |
| Удалить | `DELETE /users/{id}` |

Базовый адрес `https://dummyjson.com`. `users/api.js` экспортирует `getUsers()`,
`createUser(data)`, `updateUser(id, data)`, `deleteUser(id)` и `roleLabels`.
Функции возвращают Promise с результатом; HTTP/сеть/таймаут 15 секунд дают ошибку.
`getUsers()` возвращает уже нормализованный массив. Остальные возвращают JSON ответа.

Один человек в `app.users`:

```js
{
  id: 1,
  firstName: 'Emily',
  lastName: 'Johnson',
  username: 'emilys',
  role: 'admin', // только user / moderator / admin
  image: 'https://dummyjson.com/icon/emilys/128',
  email: 'emily.johnson@x.dummyjson.com',
  phone: '',
  description: 'Должность · Компания · Отдел'
}
```

API не имеет отдельной биографии: начальное `description` собираем из `company`.
В формах это обычный редактируемый текст; отправляем его в JSON как `description`.
Не копировать целиком объект API в интерфейс: пароли и банковские поля здесь не нужны.

DummyJSON **не сохраняет** POST/PUT/DELETE. После успешного запроса меняем локальный массив,
повторный GET не делаем. Перезагрузка возвращает исходный список.
Новому человеку выдаём `id: app.nextLocalId--` (`-1`, `-2`, …), не ID из ответа POST.
Для отрицательных ID PUT/DELETE не отправлять: таких людей на сервере нет, меняем локально.
Для положительных ID сначала дождаться успешного запроса. Никакого localStorage или общей БД.

## Как подключены части

`users/app.js` импортирует и один раз вызывает `initCreate(app)`, `initEdit(app)`, `initDelete(app)`
до первого GET. Заглушки заменить в своих файлах, названия экспортов сохранить.
Не импортировать `app.js` обратно: он уже передаёт общий объект аргументом.

| Поле/метод | Использование |
| --- | --- |
| `app.users` | Единственный массив людей; можно изменять и переприсваивать |
| `app.nextLocalId` | Следующий отрицательный ID |
| `app.ready` | Первый GET успешен, устанавливает только основа |
| `app.busy` | Сейчас выполняется операция |
| `app.setBusy(value)` | Блокирует формы/кнопки, обновляет busy, перерисовывает список |
| `app.render()` | Пересчитывает поиск, фильтр, сортировку и рисует список |
| `app.showStatus(text, isError = false)` | Сообщение на странице и внутри открытой формы |
| `app.onCreate()` | Назначает Нурда синхронно в initCreate; вызывает кнопка добавления |
| `app.onEdit(id)` | Назначает Кана синхронно в initEdit; передаётся числовой ID |
| `app.onDelete(id)` | Назначает Кыл синхронно в initDelete; передаётся числовой ID |

Готовые диалоги: `#create-dialog` / контейнер `#create-container`,
`#edit-dialog` / `#edit-container`. Открывать через `showModal()`, закрывать через `close()`.
Основа обслуживает крестики и Escape, блокирует закрытие при `busy`.
Формы создаются один раз в init, внутри `<fieldset>` — его блокирует основа.
Закрытие профиля возвращает фокус на исходную кнопку; если она удалена, фокус идёт в поиск.

Общие правила:

- В обработчиках сначала `if (app.busy || !app.ready) return;`.
- Поля: firstName, lastName — обязательные, trim, 1–60 символов; username — обязательный,
  3–30 символов, только латинские буквы, цифры, `_`, `.`, `-`, без начального `@`.
- username уникален в текущем массиве без учёта регистра; при редактировании исключить свой ID.
- role — только ключи `roleLabels`; description до 1000 символов; email необязательный `type=email`;
  phone до 40 символов; image необязательный URL только http/https.
- Перед запросом `app.setBusy(true)`, затем `try/catch/finally`; в finally `app.setBusy(false)`.
- Ошибка: `app.showStatus(error.message, true)`, массив и поля остаются как были.
- Только после успеха менять массив, вызывать render, сбрасывать/закрывать форму.
- Выводить данные через textContent/value; innerHTML допустим для постоянной разметки формы без данных.
- Передавать API только перечисленные редактируемые поля; ID передавать отдельно в updateUser.
- Во время мутации не отправлять второй запрос. Сортировка и фильтр после render должны сохраняться.

## Нурда — задание агенту

Реализуй `users/create.js`, экспорт `initCreate(app)`. Прочитай договор выше и `users/app.js`.

1. Создай форму в #create-container с полями из договора, ID с префиксом `create-` и label для каждого поля.
2. Назначь app.onCreate: очистить старое сообщение формы и открыть #create-dialog, поставить фокус на имя.
3. Submit: preventDefault, проверки busy/ready, reportValidity и дополнительные проверки договора.
4. Вызови createUser(data) из ./api.js. После успеха добавь `{ ...data, id: app.nextLocalId-- }` в app.users.
5. Перерисуй, очисти и закрой форму; сообщи «Человек добавлен».
   Если активный фильтр скрывает нового человека, уточни это в сообщении, не сбрасывай фильтр.
6. Ошибка не закрывает форму и не меняет список.

Проверки: два создания с разными отрицательными ID, пустые/пробельные поля, дубликат ника,
неверный URL, ошибка сервера, двойной submit, создание при активном фильтре.

## Кана — задание агенту

Реализуй `users/edit.js`, экспорт `initEdit(app)`. Прочитай договор выше и `users/app.js`.

1. Создай форму в #edit-container, ID с префиксом `edit-`, поля как при создании, кнопки сохранить/отмена.
2. Назначь app.onEdit(id): найди человека в app.users, запомни ID, заполни поля и открой #edit-dialog.
3. При submit заново найди человека: если его уже нет, закрой форму и покажи сообщение, не восстанавливай запись.
4. Проверь поля. Для id > 0 дождись updateUser(id, data), для id < 0 запрос не нужен.
5. После успеха Object.assign(user, data), сохрани прежний ID, render, закрыть диалог, сообщение об успехе.
6. Изменение имени должно пересортировать список; изменение роли — убрать человека из неподходящего фильтра.
7. Отмена/Escape/крестик не меняют данные. Повторное открытие берёт значения из массива, не старой формы.

Проверки: положительный/отрицательный ID, смена роли и имени при фильтре/сортировке,
дубликат ника, отмена, HTTP-ошибка с сохранением введённых полей, удалённый ID.

## Кыл — задание агенту

Реализуй `users/delete.js`, экспорт `initDelete(app)`. Прочитай договор выше и `users/app.js`.

1. Назначь app.onDelete = async function(id). Найди человека, проверь busy/ready.
2. Подтверждение через window.confirm с именем и ником. Отмена не отправляет запрос.
3. Положительный ID: deleteUser(id), проверить result.isDeleted === true; иначе выбросить ошибку.
4. Отрицательный ID: запрос не нужен. После успеха отфильтруй app.users по id и вызови render.
5. Покажи «Человек удалён», finally разблокирует интерфейс. Ошибка оставляет человека в списке.
6. После удаления верни фокус на оставшуюся кнопку списка или поле поиска, а не на body.

Проверки: отмена, серверная/локальная запись, ответ без isDeleted, HTTP-ошибка,
двойное нажатие, удаление последней записи, удаление при активном фильтре.

## Алтын — выполнено и интеграция

Готовы API, нормализация, список имя + ник + роль, модальный профиль, фото с запасными инициалами,
поиск, сортировки имени, фильтр ролей, состояния загрузки/ошибки/пустого списка и повтор GET.
Готовы точки подключения остальных модулей; товарный каталог остаётся работоспособным.
После получения трёх частей Алтын объединяет и проверяет полный CRUD.
Для объяснения: `fetch → JSON → app.users → filter → sort → DOM`; профиль открывается через `<dialog>`.

## Как работать синхронно

1. Все берут один опубликованный коммит основы из origin/main.
2. В отдельных клонах/worktree создать ветки `feature/nurda-users-create`, `feature/kana-users-edit`,
   `feature/kyl-users-delete`. Не переключать одновременно ветки в одном рабочем каталоге.
3. Каждый правит только свой модуль и свой тест. Общие HTML/CSS/API меняет Алтын по согласованию.
   Не менять товарные модули `crud/`, не реализовывать чужую часть, не переименовывать договор.
4. Каждый присылает ветку/PR с выполненными проверками. Не использовать force-push.
5. Объединение: Create → Edit → Delete. После каждого merge проверить страницу, затем общий сценарий.

## Проверка

Node.js 22.7+:

```bash
node --test tests/*.test.mjs
```

Сценарий команды: загрузить → найти по нику → отсортировать в обе стороны → выбрать каждую роль →
открыть профиль мышью и Enter → закрыть Escape → создать двух людей → изменить исходного и нового →
отменить удаление → удалить обоих → перезагрузить (возвращаются серверные данные).
Проверить ошибки GET/POST/PUT/DELETE, отсутствие дублей, мобильный экран и доступность с клавиатуры.
Новые API-тесты используют подмену fetch; реальную загрузку дополнительно проверить в браузере.
